# 화면 설계 — Streamlit 5개 화면

> 기준: `mlops-mvp-project-brief.md` 9장 + `api-v1.md`
> 프론트는 **백엔드 API만 호출**합니다 (DB·모델 파일 직접 접근 금지). 갱신은 3~5초 폴링입니다.

---

## 1. 공통

| 항목 | 내용 |
|---|---|
| 구조 | Streamlit 멀티페이지 (사이드바에서 5개 화면 이동) |
| 사이드바 | 로그인(운영자/관리자), 현재 운영 모델 버전, 백엔드 상태(`/health`) |
| 갱신 | 대시보드, 검사/추론, 재학습, 승인, 모델 관리 화면은 3~5초 주기 자동 갱신 |
| 권한 표시 | 관리자 전용 버튼(승인·거절·롤백)은 운영자에게 비활성 표시 |
| 위치 | `frontend/app.py` + `frontend/pages/` |

## 2. 화면 1 — 대시보드

**목적:** 한 화면에서 "수집 → 추론 → 학습 → 배포" 전체 상태 확인 (발표의 첫 화면)

```
┌──────────────────────────────────────────────────────┐
│ [수집: 동작중] → [추론: v1] → [학습: 대기] → [배포: v1]│
├──────────────┬──────────────┬──────────────┬─────────┤
│ 운영 모델 v1 │ 오늘 검사 N건│ 불량률 xx%   │ 승인대기 0│
├──────────────┴──────────────┴──────────────┴─────────┤
│ 최근 정확도 · 재현율 추이 차트 (드리프트 시점 표시)   │
└──────────────────────────────────────────────────────┘
```

| 구성 요소 | 내용 | 호출 API |
|---|---|---|
| 단계 상태 | 수집/추론/학습/배포 각각의 현재 상태 | `/health`, `/training/runs`, `/models/production` |
| 지표 카드 | 운영 모델 버전, 오늘 검사 건수, 불량률, 최근 정확도, 승인 대기 건수 | `/models/production`, `/predictions/stats`, `/approvals` |
| 성능 추이 차트 | 정확도·재현율 시간 추이 | `/monitoring/performance` |
| 드리프트 경고 | 성능 저하·분포 변화 경고 배너 | `/monitoring/drift` |

## 3. 화면 2 — 검사/추론

**목적:** 시뮬레이터를 켜고, 이미지가 판정되는 모습을 보여 주는 시연 중심 화면

```
┌────────────────────────────┬──────────────────────────────┐
│ 시뮬레이터 제어            │ 최신 검사 이미지 (128×128)   │
│ [시작][중지][1건 생성+판정]│ 판정: NG  점수 0.93  v1      │
│ [드리프트 켜기/끄기 ▼종류] │ 정답: NG (일치 ✔ / 불일치 ✖) │
├────────────────────────────┴──────────────────────────────┤
│ 판정 이력 표 (오판 행 강조: 미탐 빨강, 오경보 주황)       │
└───────────────────────────────────────────────────────────┘
```

| 구성 요소 | 내용 | 호출 API |
|---|---|---|
| 시뮬레이터 제어 | 시작/중지, 1건 생성+판정(정상 시나리오만), 불량률(0~1)·생성 간격(1~3초) 입력, 드리프트 켜기/끄기와 종류(어두움·노이즈·이동) 선택. 실행 여부와 드리프트 on/off 표시는 항상 서버 상태 값을 쓴다 | `/simulator/start`, `/stop`, `/generate`, `/drift`, `/simulator/status`, `/predict` |
| 최신 검사 | 가장 최근 판정의 이미지, 판정(OK/NG 큰 글자), 점수와 기준, 모델 버전, 정답 대조(일치 ✔ / ✖ 미탐 / ✖ 오경보), 판정 시간 세 값 | `/predictions`, `/inspections/{id}/image`, `/inspections/{id}`((다) 계산에만) |
| 판정 이력 | 최근 20건: 시각, 검사번호, 모델, 판정, 점수, 정답, 정오(✔ / ✖ 미탐 / ✖ 오경보), 처리(ms). **오판 행 강조** (미탐 빨강, 오경보 주황, NG 판정 글자 빨강) | `/predictions` |

- 정오 정의: 양성은 NG이다 (`/predictions/stats`의 혼동행렬과 같다). 정답 NG인데 OK로 판정 = ✖ 미탐(불량을 놓침), 정답 OK인데 NG로 판정 = ✖ 오경보.
- 판정 시간은 세 값으로 구분한다. (가) 서버 처리 시간 = 판정의 `latency_ms`, 요건은 5000 ms 이하. (나) 수동 경과 = [1건 생성+판정] 클릭 후 생성→판정→이미지 받기까지, 5초 이내 (브라우저 그리는 시간 제외). (다) 자동 생성 표시 지연 = 새 판정이 화면에 처음 나타난 시각 − 검사 생성 시각, 4초 갱신 주기 때문에 5초를 넘을 수 있어 참고값이며 합격/불합격에 쓰지 않는다.
- 1건 생성은 정상(normal) 시나리오만 제공한다. 드리프트는 자동 생성 쪽 주입으로 보여 준다.

## 4. 화면 3 — 모델 관리

**목적:** 버전 목록과 지표 비교, 롤백

| 구성 요소 | 내용 | 호출 API |
|---|---|---|
| 버전 목록 표 | 버전, 단계(후보·승인 대기(staging)·운영 중·보관(archived)·거절됨, 운영 중은 초록 강조), 생성 시각, 마지막으로 운영에 올린 사람과 시각(롤백하면 롤백한 사람과 시각으로 바뀐다, 없으면 "없음"). 운영 모델은 목록의 stage로 알고 `/models/production`은 읽지 않는다. 4초마다 서버에서 다시 읽는다 | `GET /models` (limit 없음, 전체) |
| 지표 비교 | 두 칸(A 기준, B 비교)에서 목록의 아무 버전이나 고른다. 기본값은 A = 현재 운영 모델(없으면 가장 최신), B = A를 뺀 가장 최신 버전. 정확도·재현율·정밀도·F1(정상 test_normal / 드리프트 test_drift)과 혼동행렬(양성은 NG), 차이는 B−A %p. 버전이 하나뿐이면 비교 대신 그 버전의 지표만 보여 준다 | `GET /models` 항목의 `metrics` (모델 상세를 따로 읽지 않는다) |
| 성능 추이 차트 | 이 화면에는 없다. 정확도 추이 차트는 별도 단위(④-1c)에서 다룬다 | (해당 없음) |
| 롤백 | 롤백할 버전은 보관(archived) 상태만 고를 수 있다 (서버도 그 밖은 409). 사유 입력(필수, 500자 이내) 후 [롤백]. **관리자만** 활성 (운영자는 선택칸·입력칸·버튼이 비활성이고 안내 문구가 보이며, 서버 403도 처리한다). 사유가 비어도 서버에 보내 400을 그대로 보여 준다. 응답 본문은 쓰지 않고 서버를 다시 읽은 값으로 결과를 보여 준다. 읽기 제한 시간은 8초이고, 같은 버전은 15초 안에 다시 보내지 않는다. 롤백 확인 창은 없다 | `POST /models/{version}/rollback` |
| 배포 이력 | 번호, 시각, 버전, 종류(배포/롤백), 처리자, 사유(없으면 "없음"). 최근 20건과 전체 건수를 함께 보여 준다 | `GET /deployments?limit=20` |

- 오류 처리: 400(사유 없음·500자 초과, 서버 메시지 함께), 403(권한 없음), 404(없는 버전), 409(이미 운영 중 / 다른 단계. 서버를 다시 읽은 stage로 구분한다), 503(모델을 불러오지 못함: 기존 운영 모델을 유지한다), 401(로그아웃), 서버 꺼짐(마지막 값을 시각과 함께 흐리게 보여 준다).
- 롤백이 서버에서 확인되면 `st.rerun()`을 1회 불러 사이드바의 운영 모델도 새로고침 없이 바꾼다.
- 상호작용: 롤백하면 현재 운영 모델이 바뀌어, 승인 대기 요청의 기준 모델(게이트가 비교한 모델)과 달라질 수 있다. 그러면 승인할 때 서버가 409로 거절하고, [승인] 화면이 미리 경고를 보여 준다 (api-v1.md 4장 "기준 모델 검사").
- 한계: 롤백 선택지와 버튼 활성은 직전에 읽은 목록으로 그려서 최대 4초 늦게 바뀐다 (그 사이 눌러도 서버가 409로 막는다). 배포 이력은 최근 20건까지만 읽는다. `GET /models`는 limit이 없어 버전 전체를 받는다 (버전이 많이 쌓였을 때의 응답 크기는 측정하지 않았다).

## 5. 화면 4 — 재학습

**목적:** 재학습 실행과 신·구 모델 비교, 게이트 결과 확인

| 구성 요소 | 내용 | 호출 API |
|---|---|---|
| 실행 버튼 | "재학습 실행" (운영자 이상). 직전에 읽은 서버 상태에서 실행 중이면 잠근다 (편의용이다. 방금 끝났다면 다음 갱신에서 풀리고, 실제 중복 실행 방지는 서버가 409로 한다) | `POST /training/runs` |
| 진행 상태 | 대기 → 실행 → 성공/실패, 단계별 표시 (데이터 구성 → 학습 → 평가 → 게이트). 화면에 상태를 기억하지 않고 4초마다 서버의 최근 실행 값만 보여 준다 | `GET /training/runs` (최근 목록의 첫 항목) |
| 학습 데이터 요약 | 실행 결과의 `train_data_snapshot`: train N장(고정 데이터 포함) + 이번에 편입한 pool M장. 실행 이력 표에도 같은 값을 보여 준다 | `GET /training/runs` |
| 신·구 모델 비교 | 기준 모델 vs 후보: 지표, 혼동행렬. 기준 모델은 게이트가 실제로 비교한 `baseline_version`이다. 승인 전에는 현재 production과 같고, 승인 뒤에는 production이 후보로 바뀌어도 화면은 게이트가 비교한 모델을 계속 보여 준다 | `/models/{version}` |
| 승인 요청 상태 | 게이트를 통과했으면 후보의 승인 요청이 실제로 어떤 상태인지(승인 대기, 승인됨, 거절됨)를 서버에서 읽어 보여 준다. 최근 20건에서 못 찾으면 그렇게 알린다 | `GET /approvals` (최근 20건) |
| 게이트 결과 | G1(드리프트 정확도 +1%p), G2(드리프트 재현율 −1%p 이내), G3(정상 정확도 −1%p 이내) 조건별 통과/미통과와 실제 수치 | `/training/runs/{id}` |
| 성능 저하 제안 | 재학습 화면 자체에는 배너가 없다. 드리프트 경고는 대시보드의 성능 경고 배너가 보여 주고 "재학습 화면에서 재학습을 실행할 수 있습니다"라고 안내한다 | 대시보드에서 `/monitoring/drift` |

- pool 편입: 재학습이 성공하면 학습이 읽은 pool만 train으로 편입되어 pool 건수가 줄어든다 (게이트 미통과여도 편입, 실패하면 편입하지 않음). 학습 중에 새로 쌓인 검사는 pool에 남는다.
- 화면 맨 아래 문구 3줄 (view.py와 같은 내용):
  - 한계 ① pool이 적으면 회복이 불안정할 수 있습니다. 오프라인 측정(pool 30·60·100·150·200·300장, 90회)에서 G1~G3를 모두 통과한 것은 30/90회였습니다. 60장은 기준점이 불합격이어서, 리허설에서 통과를 확인하기 전에는 쓰지 않습니다.
  - 한계 ② 평가(evaluate) 단계는 순간적으로 지나가서 화면에서 거의 보이지 않습니다 (실제 평가는 학습 단계 안에서 끝납니다).
  - 안내 ③ 게이트를 통과하면 승인 대기 요청이 자동으로 만들어집니다. 승인과 거절은 왼쪽 메뉴의 [승인] 화면에서 관리자 계정으로 합니다.

## 6. 화면 5 — 승인

**목적:** 사람이 승인하는 지점 (MLOps 핵심 정책)

| 구성 요소 | 내용 | 호출 API |
|---|---|---|
| 대기 요청 목록 | 대기(pending) 요청: 요청 번호, 후보 버전, 요청자, 요청 시각. 여러 건이면 고른 요청의 변경 요약을 보여 준다. 4초마다 서버에서 다시 읽는다 | `GET /approvals` (최근 20건) |
| 변경 요약 | 게이트가 비교한 기준 모델(`baseline_version`) 대비 후보의 지표·혼동행렬, 게이트 G1~G3 결과(게이트 결과는 학습 기록에만 있다), 현재 운영 모델 버전. 기준 모델과 현재 운영 모델이 다르면 승인할 때 서버가 409로 거절한다고 미리 경고한다 (승인 버튼은 막지 않고 서버가 판단한다) | `GET /training/runs` (최근 10건에서 후보를 만든 실행), `GET /models/{version}`, `GET /models/production` |
| 승인/거절 | 사유 입력 후 [승인] [거절]. **관리자만** 활성 (운영자는 입력칸·버튼이 비활성이고 안내 문구가 보이며, 서버 403도 처리한다). 승인 사유는 선택, 거절 사유는 필수이며 비어 있으면 서버의 400을 그대로 보여 준다. 사유는 500자 이내. 응답 본문은 쓰지 않고 서버를 다시 읽은 값으로 결과를 보여 준다. 읽기 제한 시간은 8초이고, 같은 요청은 15초 안에 다시 보내지 않는다 | `POST /approvals/{id}/approve`, `/reject` |
| 처리 이력 | 승인·거절된 요청: 요청 번호, 후보, 상태, 요청자, 요청·처리 시각, 처리자, 사유 | `GET /approvals`만 사용. `/audit-logs`는 admin 전용이라 운영자에게 403이고 같은 정보가 `/approvals`에 있어 쓰지 않는다 |

- 오류 처리: 400(거절 사유 없음), 403(권한 없음), 404(요청 없음), 409(이미 처리됨 / 기준 모델 불일치. 서버를 다시 읽은 상태로 구분한다), 503(새 모델을 불러오지 못함: 기존 운영 모델을 유지하고 요청은 대기로 남는다), 401(로그아웃), 서버 꺼짐(마지막 값을 시각과 함께 흐리게 보여 준다).
- 승인이 서버에서 확인되면 `st.rerun()`을 1회 불러 사이드바의 운영 모델도 새로고침 없이 바꾼다.
- 한계: 승인 목록은 최근 20건, 학습 기록은 최근 10건까지만 읽는다. 이 밖이면 목록에 보이지 않거나 "게이트 근거를 찾지 못했습니다"라고 표시하고, 승인은 막지 않는다 (서버가 판단한다).

## 8. 구현 시 유의점

| 항목 | 내용 |
|---|---|
| Streamlit 특성 | 버튼을 누를 때마다 스크립트가 다시 실행되므로, 로그인 정보와 선택값은 `st.session_state`에 저장 |
| 자동 갱신 | 갱신이 필요한 영역만 부분 갱신하도록 구현해 깜빡임을 줄임 |
| 구현 순서 | 화면 구현은 1번(대시보드) → 2번(검사/추론) → 4번(재학습) → 5번(승인) → 3번(모델 관리) 순서로 한다. 대시보드가 로그인·API 클라이언트·갱신 기반을 먼저 세우고, 이후 화면은 시연 흐름(보이기 → 만들기 → 학습 → 승인 → 복구) 순서를 따른다. 진행: 1번 대시보드 완료(④-1a·b), 2번 검사/추론 완료(④-2), 4번 재학습 완료(④-3), 5번 승인 완료(④-4), 3번 모델 관리 완료(④-5). 5개 화면이 모두 만들어졌고, 남은 것은 ⑤ E2E 점검이다. |
| 범위 축소 시 | 위험 신호 발생 시 모델 관리 화면의 지표 비교를 단순화 |
