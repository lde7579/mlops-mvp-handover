# 요구사항 정의서 — 자동차 부품 누락 검사 MLOps MVP

> 기준 문서: `mlops-mvp-project-brief.md` (2026-10-17) / 상태: 설계 단계 (코드 개발 착수 전)
> 본 문서는 기획서 1, 3, 14, 15장을 확정 결정 기준으로 재정리한 것입니다.

---

## 1. 목적

데이터 수집 → AI 추론 → 재학습 → 사람 승인 → 재배포가 **한 바퀴 끝까지 도는** MLOps MVP를 구현한다.
각 파트의 완성도보다 **순환 전체가 동작하는 것**을 우선한다. 프로젝트의 초점은 모델 성능이 아니라 **AI 운영**이다.

## 2. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 유스케이스 | 설비 검사 공정에서 자동차 부품 **누락** 감지 (불량 유무 OK/NG만 판정) |
| 성격 | 대학교 프로젝트 (시연 대상: 교수, 학생) |
| 인력 | 3개 파트로 역할 분리, 실제 진행은 1인 (비개발자, Claude Code 활용) |
| 인수인계 | 데이터 수집·모델 파트는 초안 작성 후 다른 분이 개선 예정 → 파트 간 계약을 문서와 테스트로 고정 |
| 환경 | 로컬 Windows PC. 개발 PC = 시연 PC. 발표 시 외부 연결 없이 동작 |
| 데이터 | 시뮬레이터가 생성하는 가상 이미지, 정상/불량 무작위, 라벨도 가상 |
| 판정 요건 | 5초 이내 |
| 승인 정책 | 모델 승격은 **사람 승인 필수** (프론트 기능) |
| 평가 조건 | 별도 채점표·필수 기술 요구 없음. 전체 기능이 돌아가는 시연이 기준 |
| 시연 방식 | 라이브 + 녹화 병행 권장 |

## 3. 범위

### 3-1. 범위 안 (In scope)

| 영역 | 내용 |
|---|---|
| 수집 | 시뮬레이터로 이미지+라벨 생성, 폴더 저장 + DB 등록, 간단 품질 체크 |
| 추론 | 소형 CNN OK/NG 분류, 예측 로그 저장, 5초 이내 판정 |
| 재학습 | 수동 버튼 / 누적 건수 / 성능 임계 트리거, 승격 게이트 |
| 승인·배포 | 사람 승인, production 승격, 롤백, 배포 이력 |
| 모니터링 | 성능 추이 차트, 드리프트(현장 변동) 감지 |
| 화면 | Streamlit 5개 화면 (대시보드, 검사/추론, 모델 관리, 재학습, 승인) |
| 인증 | 고정 계정 2개 (운영자 / 관리자) |

### 3-2. 범위 밖 (Out of scope)

| 항목 | 이유 |
|---|---|
| 누락 부품 위치 예측 | OK/NG만 판정, AI 운영 집중 |
| 메시지 브로커 (Kafka/MQTT) | 5초 이내 판정, 센서 스트림 없음 |
| MLflow, Prefect/Airflow | 자체 구현으로 대체 |
| Grafana/Prometheus | 프론트 차트로 대체 |
| Kubernetes, 클라우드 배포 | 로컬 PC 시연 |
| 현장 연동, 설비 제어(쓰기) | 범위 제외 |
| GPU 학습 | 128×128 흑백이라 불필요 |

### 현장 변동 대응 기능 (드리프트)

| 기능 | 내용 |
|---|---|
| 드리프트 주입 | 조명 어두워짐, 노이즈 증가, 부품 위치 이동을 버튼으로 주입 |
| 성능 저하 감지 | **기본:** 최근 N건 정확도(정답 라벨 기반)가 임계 이하이면 알림. **보조:** 입력 통계(평균 밝기·노이즈) 변화 검토. **NG 판정 비율 단독은 부적합** (스파이크 결과, `spike/results_detect.md`). N·T 값은 D-3에서 확정했다: 최근 30건 정확도가 0.95 미만이면 경고 (N=30, T=0.95). 확정 기록은 아래 참고 |
| 재학습 트리거 | 수동 버튼 + 성능 임계 이하 시 재학습 제안 |

**한계:** 이 MVP는 시뮬레이터가 정답(true_label)을 즉시 기록하므로 정확도 기반 감지가 가능하다. 실제 현장에서는 정답이 늦게 오거나 아예 없을 수 있고, 그 경우 정확도를 쓸 수 없다. 정답 없이 쓸 수 있는 신호에도 한계가 있다. NG 판정 비율은 드리프트와 진짜 불량 증가를 구별하지 못했고, 입력 통계(평균 밝기·노이즈)는 dark·noise에서 큰 변화가 관찰되었으나 shift에서는 변화가 없었다(감지 규칙으로 평가하지는 않음). 이 한계는 발표에서 함께 설명한다.

**감지 N·T 확정 기록 (D-3, 2026-10-31):**
- 측정: 서버를 돌리지 않고 정답/오답 열을 오프라인으로 재생해 N(10, 15, 20, 30, 50)과 T(0.90, 0.93, 0.95, 0.96, 0.97, 0.98) 격자를 평가했다. 정상·dark·noise·shift 스트림을 종류마다 20개씩 썼다. 합격 판정은 v1 시드 42(`models/v1`)로만 했고, 시드 43·44 수치는 참고이며 합격 판정에 쓰지 않았다. 결과는 `data/detection_report.txt`(`scripts/measure_detection.py`)에 있다.
- 원래 선택 규칙(측정 전에 고정): 헛경고, dark 탐지, dark 회복 합격을 모두 만족하는 (N, T) 중 N이 가장 큰 것, 같으면 T가 낮은 것. 이 규칙의 결과는 N=50, T=0.90이었다. 이때 dark 회복(v2로 바뀐 뒤 경고가 꺼지기까지)이 2초 간격에서 100초라 시연 배분 2분(e2e-scenario.md 4장)에 빠듯했다.
- 규칙 개정: 개정 1·2는 모두 **측정 결과를 확인한 뒤에 한 것**이다.
  - 개정 1: 합격 항목에 "dark 회복 2초 간격 60초 이내(N ≤ 30)"를 추가했다. 사유는 위 시연 배분 2분이다. 원래 규칙에 시간 제한이 없어 N=50이 뽑혔다.
  - 개정 2: 동점 처리 "T가 낮은 것"을 "오답 1건에 경고가 켜지지 않는 칸(k ≥ 2) 중 dark 탐지가 가장 빠른 T"로 바꿨다. 사유는 시드 42에서 T가 헛경고에 영향을 주지 못해(아래 한계) "T가 낮은 것"에 근거가 없기 때문이다. 이 조건에서도 동점이 남으면(N=30에서 T=0.95와 0.96은 모든 항목이 같다) 낮은 T를 택한다.
- 개정 규칙의 결과는 N=30, T=0.95(오답 2건부터 경고)이며, **이전 권장 수치와 같다.** 대안으로 본 N=30, T=0.97은 dark·noise 탐지가 더 빠르지만 오답 1건에도 경고가 켜져 제외했다.
- 확정값의 측정 결과(시드 42): dark는 주입 후 경고가 켜지기까지 중앙값 5.5건(2초 간격 11초, 대시보드 폴링 지연 최대 +5초 별도)이고, 회복은 v2 판정이 30건 쌓인 뒤(2초 간격 60초) 경고가 꺼진다.
- 한계:
  - 시드 42는 정상 스트림 오답이 0건이라 헛경고 기준이 모든 (N, T) 칸에서 자동으로 통과했고 칸을 가르지 못했다. 헛경고는 v1 학습 시드에 크게 좌우된다. 참고(합격 판정에 쓰지 않음): 시드 43은 정상 정확도가 0.971이고 N=30, T=0.95에서 시연 150건 동안 경고가 없는 스트림이 20%뿐이었다.
  - noise는 경계 사례다. N=30, T=0.95에서 주입 후 N건 이내 탐지가 15%, 끝까지 탐지가 90%이고, 탐지까지 걸린 건수의 중앙값이 65.5건(2초 간격 131초)이다.
  - shift는 탐지는 되지만(N건 이내 탐지 90%) v2로 바뀐 뒤에도 회복이 안정적이지 않다(채워지자마자 꺼지고 재점등이 없는 스트림 45%). 한계 설명용이며 회복 합격 기준을 두지 않았다.

## 6. 비기능 요구사항

| 항목 | 기준 |
|---|---|
| 판정 시간 | 5초 이내 (스파이크에서 실측) |
| 재학습 시간 | 목표 1분 이내 (라이브 시연용, 스파이크에서 확인) |
| 미탐 대응 | 불량 미검출이 더 치명적이므로 재현율 우선, 임계값 조정 가능 |
| 학습·추론 일관성 | 전처리는 `common/preprocess.py` 한 곳에서 공유 |
| 실패 안전성 | 모델 교체 시 로딩 실패하면 기존 모델 유지 |
| 감사 | 승인·롤백·배포는 감사 로그에 기록 |

## 7. 성공 기준

E2E 시나리오(`e2e-scenario.md`)의 8단계가 화면에서 한 번에 끝까지 동작한다.
