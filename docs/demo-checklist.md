# 시연 체크리스트

> 대상: 시연하는 사람 (프로젝트 담당자). 기준: `e2e-scenario.md` 8단계, `scripts/reset_demo.py`.
> 모든 명령은 PowerShell이고 프로젝트 폴더에서 실행한다.
> 화면(`frontend/`, Streamlit)은 대시보드(화면 1), 검사/추론(화면 2), 모델 관리(화면 3), 재학습(화면 4), 승인(화면 5)의 5개가 모두 만들어져 있다. 남은 것은 ⑤ E2E 점검이다. 검사/추론은 3장·4장 1번을, 재학습은 4장 3번을, 승인은 4장 4번을, 롤백은 4장 6번을 화면 조작으로 대신할 수 있다. 각 번호의 API 명령도 그대로 쓸 수 있다.
> 수치는 확정된 것(N=30, T=0.95 등)만 적었다. 측정하지 않은 것은 "미측정"으로 표시했고 리허설에서 채운다.

```powershell
cd $HOME\Documents\mlops-mvp
.\.venv\Scripts\Activate.ps1
```

## 1. 시연 전 (서버 끄고)

1. 서버 창을 닫는다. `reset_demo`는 서버가 켜져 있으면 `--yes`를 줘도 거부한다.
   단, 확인하는 것은 8000번 포트뿐이다. 다른 포트로 켠 서버는 못 잡으니 서버 창은 직접 닫는다.
2. 미리보기: 지울 것을 보기만 한다. 아무것도 바꾸지 않는다.
   ```powershell
   python -m scripts.reset_demo
   ```
   기대 출력 첫 줄: `== 시연 초기화 (미리보기: 아무것도 바꾸지 않습니다) ==`
   (`DB 행`, `data/pool PNG`, `지울 모델 폴더`, `유지: models/v1 …` 줄이 이어서 나온다. 시작할 때 torch를 불러오느라 몇 초 걸린다.)
3. 실제 초기화.
   ```powershell
   python -m scripts.reset_demo --yes
   ```
   기대 출력 마지막 줄: `합격 - 처음 상태입니다 (검사·판정·승인·학습·배포·감사 0건, v1 production, pool PNG 0장).`
   지우는 것: DB의 검사·판정·승인·학습·배포·감사 로그, `data/pool`의 PNG, `models/v2` 이상 폴더. v1은 production으로 다시 등록한다.
   남기는 것: `models/v1`, `data/dataset`, `data/secret.key`.
   중간에 실패하면 같은 명령을 다시 실행한다 (이어서 지운다).
4. 처음 상태 확인 (읽기만 한다, 파일을 만들거나 바꾸지 않는다).
   ```powershell
   python -m scripts.reset_demo --check
   ```
   기대: 마지막 줄 `합격 - 처음 상태입니다 …`, 종료코드 0 (`$LASTEXITCODE` → `0`).
   불합격이면 남은 항목이 `  - …` 로 나온다.
5. v1 파일이 그대로인지 확인. 초기화는 `models/v1`을 건드리지 않으므로 **초기화 전과 후의 값이 같으면 정상**이다.
   ```powershell
   Get-FileHash models\v1\* | Select-Object Hash, Path
   ```
   기대: 초기화 전에 한 번, 초기화 후에 한 번 실행해 두 값이 같다.
   참고(2026-10-31 이 PC 기준, 앞 8자리만): `model.pt` → `6533E22B…`, `metrics.json` → `CE22E6C7…`. v1을 다시 학습하면 값이 달라지는 것이 정상이다.
6. pool 폴더가 비었는지 확인.
   ```powershell
   (Get-ChildItem data\pool -Filter *.png).Count
   ```
   기대: `0`
7. 초기화 후에는 검사 번호가 `INS-000001`부터, 학습 후보는 `v2`부터 다시 시작한다 (같은 시드라 같은 이미지가 나온다).

## 2. 서버 켜기

1. 서버 시작 (창을 하나 더 열어 둔다).
   ```powershell
   python -m uvicorn backend.main:create_app --factory --port 8000
   ```
   기대: `Uvicorn running on http://127.0.0.1:8000`
2. 운영 모델이 올라올 때까지 기다린다. 모델은 서버가 켜질 때 미리 불러온다. 서버 시작 명령부터 `/health`가 응답할 때까지 임시 폴더(샌드박스) 기준 약 8~11초 걸렸다 (모델 미리 불러오기 포함, 2회 측정: 10.8초, 8.3초). 이전 측정(`data/latency_report.txt` 항목 1, 5회 재시작)은 5.1~7.7초(중앙값 5.6초)였다. 두 측정은 방법이 달라 하나의 값으로 합치지 않았다. 시연 PC에서의 값은 리허설에서 다시 잰다.
   ```powershell
   (Invoke-RestMethod http://127.0.0.1:8000/health).model
   ```
   기대: `production_version` = `v1`, `loaded` = `True`
   `loaded`가 `False`면 시작하지 않는다. `python -m scripts.reset_demo --check`와 `models\v1` 폴더를 먼저 본다.
3. 로그인 (토큰을 `$h`에 담는다. admin은 운영자 권한도 모두 가진다).
   ```powershell
   $pw = Read-Host "admin 비밀번호"
   $tok = (Invoke-RestMethod -Method Post http://127.0.0.1:8000/auth/login -ContentType 'application/json' -Body (@{username='admin';password=$pw} | ConvertTo-Json)).access_token
   $h = @{ Authorization = "Bearer $tok" }
   ```
   기대: 출력 없음 (`$tok`에 값이 들어간다)
4. 미리 한 번 호출해 둔다 (prewarm). 입력 분포의 기준 통계를 첫 호출 때 계산하므로, 청중 앞에서 처음 계산하지 않게 한다.
   ```powershell
   Measure-Command { Invoke-RestMethod http://127.0.0.1:8000/monitoring/drift -Headers $h | Out-Null }
   ```
   기대: 오류 없이 끝남. 걸린 시간은 미측정, 리허설에서 기록한다.
5. 경고 기준 확인 (N=30, T=0.95로 확정).
   ```powershell
   (Invoke-RestMethod http://127.0.0.1:8000/monitoring/drift -Headers $h).performance_warning
   ```
   기대: `recent_n` = `30`, `accuracy_threshold` = `0.95`, `confirmed` = `True`, `active`는 비어 있음 (판정 30건 미만이라 판단 보류)
6. 화면 켜기 (창을 하나 더 열어 둔다). 화면은 백엔드 API만 부르고, 서버 주소는 환경 변수 `MLOPS_API_URL`(기본 `http://127.0.0.1:8000`)이다.
   ```powershell
   python -m streamlit run frontend/app.py --server.port 8501 --server.address 127.0.0.1
   ```
   기대: `Local URL: http://localhost:8501`. 브라우저에서 이 주소를 연다.
   `--server.address 127.0.0.1`을 빼면 같은 네트워크의 다른 PC에서도 화면에 접속할 수 있으니 빼지 않는다.
   왼쪽 사이드바에서 로그인한다 (계정은 운영자 `operator`, 관리자 `admin`, 비밀번호는 `backend/README.md`의 시연 계정 표). 새로고침하면 다시 로그인해야 한다 (토큰은 화면 세션에만 보관한다).
   화면이 켜져 있어도 `reset_demo`는 8000번 포트의 서버만 확인하므로, 초기화 전에 서버 창과 화면 창을 둘 다 닫는다.
   실화면 확인 (2026-11-01, 임시 폴더 서버로 수행): 로그인, 카드 6개, 경고 3상태(회색·초록·빨강), 4초 자동 갱신, 드리프트 주입 표시, 서버 꺼짐 표시와 같은 비밀키 재시작 후 자동 복구가 모두 기대대로 동작했다. 한계: 서버가 꺼진 동안 사이드바의 `백엔드 상태`·`운영 모델`은 새로고침 전까지 이전 값("정상")을 유지한다 (본문은 빨간 줄로 바뀐다). 승인 후 "모델 교체 직후" 경고 문구는 실화면에서 확인하지 못했다 (미확인).

## 3. 판정·NG 확인 (단계 1~2)

화면으로 하려면: 사이드바에서 로그인 → 왼쪽 메뉴 [검사/추론] → [시작] (불량률 0.2, 간격 2.0이 기본값) → 이력 표와 '최신 검사'에서 NG 확인. 아래 API 명령과 같은 결과이고, 둘 중 한 방법으로 진행한다.

1. 시뮬레이터 시작 (정상 모드, 기본 불량률 0.2, 2초 간격).
   ```powershell
   Invoke-RestMethod -Method Post http://127.0.0.1:8000/simulator/start -Headers $h
   ```
   기대: `running` = `True`
2. 약 5초 뒤 판정 확인. 불량 순서는 고정(`LABEL_SEED=42`)이라 **2번째 검사(INS-000002)가 NG일 것으로 예상**한다. 이는 난수 순서를 코드로 계산한 **코드 기준 예상이며, 첫 리허설에서 확인 전**이다. 임시 폴더 서버와 화면 점검(2026-11-01)에서는 INS-000002가 NG(정답 NG, 점수 0.85)로 나와 예상과 맞았다. 시연 PC 첫 리허설 확인은 아직이다.
   ```powershell
   (Invoke-RestMethod "http://127.0.0.1:8000/predictions?limit=5" -Headers $h).items | Select-Object inspection_id, true_label, predicted_label, latency_ms
   ```
   기대: 검사가 2건 이상 나오고 `INS-000002`의 `true_label`·`predicted_label`이 모두 `NG`. 모든 `latency_ms` ≤ 5000.
   NG가 안 보이면 불량률을 바꿨거나 예상이 틀린 것이다. 리허설 때 멈추고 원인을 본다.
3. 합격 기준 (e2e 단계 1·2): 10초 안에 새 검사 3건 이상, 모든 건이 `data_split=pool`, 판정이 저장됨.
   ```powershell
   (Invoke-RestMethod "http://127.0.0.1:8000/inspections?limit=3" -Headers $h).total
   ```
   기대: 숫자가 올라간다 (10초 뒤 3 이상).

실화면 확인 (2026-11-01, 임시 폴더 서버): 화면 코드를 자동 실행해 점검한 결과 시작/중지/드리프트 상태가 서버 값으로 표시, NG 판정 표시, 수동 1건 생성+판정, 서버 꺼짐 표시와 자동 복구가 기대대로 동작했다. 같은 검사의 이미지를 다시 받지 않는 것도 서버 로그로 확인했다. 한계: ① 색·배치는 2026-11-01 사용자가 브라우저로 직접 확인했다 (이미지, NG 빨강 글자, 오경보 주황 배경, 1건 생성 경과 문구, 시작 버튼 비활성, 드리프트 켜기/끄기, 중지). 시연 PC에서의 첫 리허설 확인은 아직이다. ② 시작/중지 버튼의 활성 여부는 직전 갱신 기준이라 누른 뒤 최대 4초 늦게 바뀐다. ③ 실행 중이면 시작 버튼이 비활성이라 "이미 실행 중" 안내는 화면에서 재현되지 않고 자동 시험으로만 확인했다 (서버가 409를 주는 것은 직접 확인).

## 4. 대본 (dark 위주)

종류는 **dark만** 시연한다. 이유: 경고가 켜지고 꺼지는 시간이 확정 수치로 설명 가능하다.

1. 드리프트 주입 (단계 3).
   ```powershell
   Invoke-RestMethod -Method Post http://127.0.0.1:8000/simulator/drift -Headers $h -ContentType 'application/json' -Body '{"enabled":true,"drift_type":"dark"}'
   ```
   기대: `drift.enabled` = `True`, `drift.drift_type` = `dark`
   말할 것: 최근 30건 정확도가 0.95 미만이면 경고 (N=30, T=0.95). dark는 주입 후 경고까지 중앙값 5.5건 (2초 간격 약 11초, 화면 갱신 지연은 최대 +5초 별도).
   화면으로 하려면: [검사/추론]에서 '드리프트 종류'를 '어두움'으로 두고 [드리프트 켜기]. 상태 줄에 '드리프트 주입: 어두움'이 서버 값으로 표시된다.
   시연 주의: dark를 켜면 이력 표에 주황색 오경보 행(✖ 오경보)은 나오지만 빨간 미탐 행(✖ 미탐)은 나오지 않을 수 있다. 임시 폴더 점검에서 드리프트 검사 148건 중 미탐 0건, 오경보 40건이었다 (어두워지면 정상을 불량으로 잘못 보는 쪽으로 틀렸다. 3-D의 "재현율 유지, 오경보 증가"와 같은 방향).
2. 경고 확인.
   ```powershell
   (Invoke-RestMethod http://127.0.0.1:8000/monitoring/drift -Headers $h).performance_warning
   ```
   기대: `active` = `True`
3. 재학습 (단계 4~5). 재학습 요청은 신규 데이터(`data_split=pool`)가 **1건 이상**이어야 받아 준다. 이것은 API가 요구하는 최소 조건일 뿐이고, **시연에 권장하는 pool 건수는 리허설에서 확정한다** (5장 1번). 요청 응답의 `run_id`를 변수에 담아 쓴다.
   ```powershell
   $run = Invoke-RestMethod -Method Post http://127.0.0.1:8000/training/runs -Headers $h
   Invoke-RestMethod "http://127.0.0.1:8000/training/runs/$($run.run_id)" -Headers $h | Select-Object status, step, result_version
   ```
   기대: 두 번째 명령을 반복하면 `queued` → `running` → `succeeded`, `result_version` = `v2`. 이전 측정 38.4초 (pool 500장 기준). 이번 시연의 pool 건수와 소요 시간은 미측정.
   게이트 통과 시 승인 요청이 자동으로 생긴다. 미통과면 v2는 `rejected`가 되고 승인 요청이 없다 (e2e X1). 이 경우 5장 1번의 측정 결과에 따라 대본을 조정한다.
   화면으로 하려면: 왼쪽 메뉴 [재학습] → [재학습 실행]. 진행 4칸(데이터 구성·학습·평가·게이트)과 게이트 G1~G3, 신·구 지표, 승인 요청 상태, 실행 이력이 4초마다 서버 값으로 갱신된다. 승인은 [승인] 화면(아래 4번)에서 한다.
   실화면 확인 (2026-11-01, 임시 폴더 서버): 샌드박스 1회 점검, 일반화하지 않음. 측정 90회 중 30회 합격, 권장 pool 건수 없음 유지. pool 120장으로 재학습 54.3초 (prewarm 후. 120장 기준이라 pool 500장 기준 38.4초와 비교하지 않는다). 게이트 G1 드리프트 정확도 0.854 → 0.914 통과. 관리자 승인 후 화면에 "승인됨" 표시. 409는 두 종류 확인 ("이미 실행 중", "신규 데이터 없음 pool 0건"). 학습 중 GET /training/runs 응답은 1회차 평균 15ms·최대 89ms, 2회차 평균 13ms·최대 41ms. pool 편입 실측: 시작 직전 120, 학습 중 생성 50, 편입 120, 완료 후 50 (120 + 50 − 120 = 50).
   브라우저 확인 (2026-11-01, 사용자가 직접 확인, 이상 없음): 실행 이력, G1~G3 행, 신·구 지표와 혼동행렬, 승인 대기 표시, 한계 문구와 pool 편입 문장이 기대대로 보였고 색이 깨지지 않았다.
   한계: ① 실서버에서 게이트 미통과·실패·403·503은 만나지 못해 단위 시험으로만 확인했다. ② 시연 PC에서의 첫 리허설 확인은 아직이다.
4. 승인 (단계 6, admin). 대기 중인 승인 요청의 id를 목록에서 꺼내 변수에 담는다.
   ```powershell
   $apr = (Invoke-RestMethod "http://127.0.0.1:8000/approvals?status=pending" -Headers $h).items[0].approval_id
   Invoke-RestMethod -Method Post "http://127.0.0.1:8000/approvals/$apr/approve" -Headers $h
   ```
   기대: 첫 명령은 출력 없음 (`$apr`에 `APR-…` 값). 두 번째 명령은 `new_version` = `v2`, `old_version` = `v1`, `reload.loaded_version` = `v2`
   화면으로 하려면: 관리자로 로그인 → 왼쪽 메뉴 [승인] → 대기 요청과 변경 요약(게이트 G1~G3, 신·구 지표)을 보고 사유를 적은 뒤 [승인]. 거절은 사유가 필수다. 운영자로 들어가면 사유칸과 두 버튼이 비활성이고 "관리자만" 안내가 보인다. 승인이 서버에서 확인되면 사이드바 운영 모델이 새로고침 없이 바뀐다.
   실화면 확인 (2026-11-01, 샌드박스 8001, 사용자 브라우저, 1회 점검, 일반화하지 않음): 운영자 버튼 비활성, 사유 없는 거절 400, 승인 후 사이드바 새로고침 없이 갱신, baseline 불일치 409 문구, 처리 이력, 서버 껐다 켜기 후 화면 복구. 점검 순서는 실제로 "v3 승인 → v2 승인 시도(baseline 불일치 409) → v2 거절"이었고 최종 상태는 v3 production, v2 rejected, v1 archived다 (계획의 "v2 승인" 순서가 아니었다).
   샌드박스 실측 (1회): v2는 pool 120장, 학습 58.1초, G1 드리프트 정확도 0.854 → 0.914 통과. v3는 pool 67장, 학습 52.7초, G1 1.000 통과 (일반 성능이 아니라 이 1회의 값). 서버 재기동 후 loaded=true까지 11.9초.
   API 확인 (같은 샌드박스): 운영자 토큰으로 approve·reject 모두 403이다 (처리 끝난 요청에서도 409가 아니라 403, 권한 검사가 상태 검사보다 먼저). 관리자 토큰으로 이미 처리된 요청을 다시 승인하면 409.
   한계: ① 403은 화면 조작으로 만들 수 없다 (운영자는 버튼이 비활성). ② 승인 중복 클릭은 실화면에서 관찰하지 못했다 (시험의 15초 표식과 서버 409로만 확인, ⑤ 단계에서 관찰). ③ "모델 없이 켠 서버의 첫 승인 약 5.7초"는 샌드박스가 v1을 불러온 채 켜져 재현되지 않아 미검증이다 (torch 첫 로딩 약 4.8초가 포함된 값, ⑤ 단계에서 확인). ④ 승인 목록은 최근 20건, 학습 기록은 최근 10건까지만 읽는다. ⑤ 시연 PC에서의 첫 리허설 확인은 아직이다.
5. 회복 확인 (단계 7). 새 판정부터 `model_version`이 `v2`. 경고는 최신 30건이 모두 v2 판정이어야 판단하므로, 그 전에는 판단 보류다. 2초 간격이면 v2 판정 30건(약 60초) 뒤 경고가 꺼진다.
   ```powershell
   (Invoke-RestMethod http://127.0.0.1:8000/monitoring/drift -Headers $h).performance_warning
   ```
   기대: 처음엔 `active`가 비어 있고(판단 보류), 약 60초 뒤 `active` = `False`
6. (옵션) 롤백 (단계 8). 사유가 필요하다.
   ```powershell
   Invoke-RestMethod -Method Post http://127.0.0.1:8000/models/v1/rollback -Headers $h -ContentType 'application/json' -Body '{"reason":"시연 롤백"}'
   ```
   기대: `new_version` = `v1`
   화면으로 하려면: 관리자로 로그인 → 왼쪽 메뉴 [모델 관리] → 롤백할 버전(보관(archived) 상태만 고를 수 있다)을 고르고 사유를 적은 뒤 [롤백]. 사유가 없으면 서버가 400으로 거절한다. 운영자로 들어가면 선택칸·사유칸·버튼이 비활성이고 "관리자만" 안내가 보인다. 롤백이 서버에서 확인되면 사이드바 운영 모델이 새로고침 없이 바뀌고, 배포 이력 표에 롤백 행이 생긴다.
   실화면 확인 (2026-11-01, 샌드박스 b1, 사용자 브라우저, 1회 점검, 일반화하지 않음): 운영자 버튼 비활성과 안내, 사유 없는 롤백 400, 롤백 선택지는 보관(archived) 버전만, v1 롤백 후 사이드바 새로고침 없이 갱신, 배포 이력에 롤백 행, 검사/추론의 새 판정 model_version v1, A/B 지표 비교, 서버 껐다 켜기 후 화면 복구와 롤백 결과(v1 운영) 유지. 점검 시작 때 상태는 v3 production, v2 rejected, v1 archived였다.
   API 확인 (같은 샌드박스): 운영자 토큰으로 롤백하면 403이다 (거절된 v2에서도 409가 아니라 403, 권한 검사가 상태 검사보다 먼저). 관리자가 거절된 v2를 롤백하면 409 ("v2: archived 가 아니라 rejected 라서 롤백할 수 없습니다"). 호출 전후 모델 단계와 배포 이력 건수는 변하지 않았다.
   샌드박스 측정 (이 샌드박스 5회, 일반화하지 않음): `GET /models` 평균 5.9ms 최대 7.4ms 1746바이트, `GET /deployments?limit=20` 평균 9.0ms 최대 21.9ms 599바이트 (버전 3개·이력 4건 기준). 서버 재기동 후 `loaded=true`까지 11.9초 (복사본 첫 launch는 13.3초).
   한계: ① 403은 화면 조작으로 만들 수 없다 (운영자는 버튼이 비활성). ② 롤백 중복 클릭은 실화면에서 관찰하지 못했다 (시험의 15초 표식과 서버 409로만 확인, ⑤ 단계에서 관찰). ③ 모델 없이 켠 서버의 첫 롤백과 롤백 요청~응답 소요 시간은 이번 점검에서 측정하지 않았다 (⑤ 단계에서 확인). ④ 롤백 선택지는 직전 갱신 기준이라 최대 4초 늦게 바뀐다. ⑤ 시연 PC에서의 첫 리허설 확인은 아직이다.
7. 질문이 나오면: noise는 경계 사례(경고까지 중앙값 65.5건≈131초), shift는 한계 설명용 (탐지는 되지만 v2로도 회복이 안정적이지 않음). 이 MVP는 시뮬레이터가 정답을 바로 알려 주므로 정확도 기반 감지가 가능하다. 실제 현장은 정답이 늦거나 없을 수 있다는 한계도 함께 말한다.

## 5. 리허설 재측정 항목

e2e-scenario.md 5장과 같이 `reset_demo` 후 처음부터 **3회** 반복해서 기록한다.

1. **[필수] pool 건수별 회복도 측정 (오프라인 측정 완료, 시연 조합은 리허설에서 사전 통과 확인).** 지금 방식은 pool 0장에서 시작해 시연 중 시뮬레이터가 쌓는다. 단계 1~3을 지난 시점의 pool이 적으면 회복도가 낮아 게이트 G1(+1%p)을 못 넘을 수 있다 (실제 시연이 X1 경로로 빠질 위험). 서버와 실제 DB 없이, 시연과 같은 방식(정상 N1장 뒤 dark N2장)으로 pool을 만들어 v2를 임시 학습해 쟀다 (출처: `data/pool_recovery_report.txt`, `data/pool_recovery_ab_report.txt`).
   측정 결과 (확정):
   - 90회 측정 (pool 크기 30·60·100·150·200·300 × dark 비율 20·40·60%, 반복 5회): G1~G3를 모두 통과한 것은 30/90회. 학습 시드별 합격은 시드 42(이미지 시드 43) 14/18, 43이 1/18, 44가 7/18, 45가 0/18, 46이 8/18.
   - 이 측정은 회차마다 학습 시드와 이미지 시드가 함께 바뀌어 원인을 나누지 못했다. 그래서 분리 측정 27회 (크기 60·100·150, dark 60%)를 했다: 학습 시드 42 고정 + 이미지 시드 변경은 11/15, 이미지 시드 43 고정 + 학습 시드 변경은 8/15 (기준점 1회를 양쪽에 넣은 크기당 5개 점).
   - 기준점 (학습 시드 42, 이미지 시드 43): 크기 60은 불합격 (G1 -5.40%p), 크기 100은 합격 (+7.00%p), 크기 150은 합격 (+14.60%p). 90회 측정의 회차 1과 분리 측정의 기준점에서 같은 값이 나왔다. 같은 입력이면 학습 결과가 같다는 뜻이다.
   - 이미지 시드를 바꾸면 크기 150은 5개 점 중 3개만 합격했다 (크기 60·100은 4개). 학습 시드를 바꾸면 크기 60·100은 2개, 크기 150은 4개가 합격했다.
   - 측정 전에 정한 규칙(칸 합격 = 통과율 80% 이상 + 시연 재현 합격, 더 큰 크기도 모두 합격)으로는 합격한 pool 건수가 없다. 그래서 **권장 pool 건수는 측정 규칙상 없음**이다. 이 문서에서 건수를 확정하지 않는다.
   원인 (추정, 검증하지 않음): 실패한 회차 중에는 dark 구간 정확도는 높은데 noise·shift 구간이 크게 낮은 것이 있다 (예: 분리 측정 크기 60, 학습 시드 46: dark 1.000, noise 0.563, shift 0.464). 한 종류의 드리프트만 쌓인 pool로 학습하면 다른 종류에서 흔들릴 수 있다고 추정한다. dark 구간이 낮아서 실패한 경우도 있다 (분리 측정 기준점 크기 60: dark 0.713, shift 0.693).
   미측정: dark 20%·40%에서의 시드 분리, 크기 200 이상에서의 시드 분리, 재학습을 누른 실제 시점의 건수(정상 N1, dark N2)에서의 통과, noise·shift가 섞인 pool, 서버를 거친 실제 시연 흐름.
   시연 방식 (결정): 학습 시드 42(서비스 기본값)와 이미지 시드 43(`reset_demo` 직후 같은 이미지가 나옴)은 고정이다. 시연마다 달라지는 것은 재학습을 누른 시점의 pool 구성뿐이다. 그래서 **리허설에서 게이트 통과를 미리 확인한 pool 건수·구성 조합만 대본에 쓴다.** 크기 60은 기준점(시드 42·이미지 43)이 불합격이었다 (이미지 시드가 달라지면 합격한 경우도 있음). 리허설 확인 없이 쓰지 않는다. 사전에 통과를 확인하지 못한 건수로 시연하면 X1 경로(미통과, rejected)로 빠질 수 있다.
   기록: 재학습을 누른 시점의 pool 건수, v2의 G1·G2·G3 수치, 게이트 통과 여부.
   pool 건수는 대시보드의 `pool 건수` 카드 또는 재학습 화면 위쪽의 "pool 건수" 줄에서 읽는다 (둘 다 4초마다 갱신. 실화면에서 서버가 만든 검사 수와 같게 늘어나는 것을 확인했다). 학습이 성공(succeeded)하면 읽은 pool은 train으로 편입되어 줄어들고(게이트 미통과도 편입), 실패(failed)하면 편입하지 않는다 (백엔드 재학습 코드 기준). 그래서 재학습을 누르기 직전의 값을 적는다. 카드를 볼 수 없으면 같은 값을 API로 조회한다 (`$h`는 2장 3번에서 만든 토큰 헤더):
   ```powershell
   (Invoke-RestMethod "http://127.0.0.1:8000/inspections?data_split=pool&limit=1" -Headers $h).total
   ```
   결과에 따라 대본의 대기 시간 또는 pool 선투입 방식(별도 단위, 별도 승인)을 정한다.
2. 재학습 시간: 목표 1분 이내. 이전 측정 38.4초 (pool 500장 기준). 이번 방식의 값은 미측정.
3. 판정 시간: 세 값으로 나눠 기록한다. (가) 서버 `latency_ms` ≤ 5000 (요건, 화면의 '서버 처리 N ms'와 `/predictions`). (나) [1건 생성+판정]을 누른 뒤 판정과 이미지를 받을 때까지의 경과 N.N초, 5초 이내 (e2e 2단계 '5초 이내 OK/NG 표시'. 화면 문구 '이번 수동 판정: …'. 브라우저 그리는 시간 제외). (다) 자동 생성은 생성 시각부터 화면 표시까지의 지연이며 참고값이다 (4초 갱신 주기와 생성 간격 때문에 5초를 넘을 수 있고 합격/불합격에 쓰지 않는다). 측정 (2026-11-01, 임시 폴더 서버, 같은 PC, 브라우저 그리기 제외): (가) 서버 처리 2~7 ms, (나) 5회 0.04~0.20초 (첫 1회가 0.20초). (다)는 갱신 시점에 따라 달라져 값을 정하지 않았다. 시연 PC 리허설에서 재측정 예정.
4. `loaded=true`까지 걸리는 시간은 임시 폴더 기준 8~11초(2장 2번 참고)이고 시연 PC 값은 미측정, prewarm 소요 시간은 미측정.
5. 경고 켜짐/꺼짐 시간: 확정 수치(켜짐 중앙값 5.5건≈11초, 꺼짐 v2 30건≈60초)와 비교해 크게 어긋나면 기록한다.
6. 인터넷을 끊은 상태에서 8단계가 모두 동작하는지, 녹화 영상 준비 (e2e-scenario.md 5장).
7. 승인 화면 확인 (⑤ 단계): 승인 중복 클릭 관찰, 모델 없이 켠 서버의 첫 승인 소요 시간 (읽기 제한 8초 안에 들어오는지). 값은 미측정, 리허설에서 기록한다.
8. 모델 관리 화면 확인 (⑤ 단계): 롤백 중복 클릭 관찰, 모델 없이 켠 서버의 첫 롤백과 롤백 요청~응답 소요 시간 (읽기 제한 8초 안에 들어오는지). 값은 미측정, 리허설에서 기록한다.
